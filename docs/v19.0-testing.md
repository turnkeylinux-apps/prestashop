## Scope and source decision

Debian 13 Trixie does not package the PrestaShop server. The appliance installs
the official PrestaShop 9.1.5 Classic production archive from PrestaShop's
distribution site. The August 2026 source review recorded upstream publication of 9.1.5 on
2026-08-18 as the final planned 9.1 maintenance release, including five security
fixes; 9.2 was then in beta. Recheck support and security releases at the release
cutoff rather than treating that historical selection as current release advice.
The build pins and verifies SHA-256
`37140cb77c03acf61b832f76893cd8fe1e304b0fc14fa5485cfea4a7bfaf3a72`.
The distribution channel does not publish a detached digest for this archive,
so the trust boundary is the official HTTPS origin plus the repository-pinned
digest.

The candidate installs official Update Assistant 7.6.6 from the PrestaShop
GitHub organization, pinned to SHA-256
`5a0fc646a487f764355cf9a5dc990827dc692ac3c98493395c7e7360913177a8`.
Verify the downloaded release asset against that pin and its upstream-published
digest. The assistant provides supported web and command-line update flows;
the configured reference above exercised its update and restore paths.

PHP 8.4, MariaDB, Apache, Postfix, Adminer and the PHP extensions come from the
signed Debian Trixie repositories. Webmin and its Apache, PHP and MariaDB
modules come from the signed TurnKey Trixie repository. PrestaShop 9.1 supports
PHP 8.1 through PHP 8.5, which includes Trixie's PHP 8.4.

## Required journey on the delivered image

Record image digest, source revision, installed application/updater/runtime
versions, deployment format and setup inputs. Inspect applicable user reports,
including the November PrestaShop forum incident and
[tracker #1900](https://github.com/turnkeylinux/tracker/issues/1900).
Distinguish reported behavior, reproduction, source correction and verification
in the candidate. Exercise only supported configuration interfaces and plugins;
keep upstream core and source templates unpatched; use upstream generators for
derived files.

1. Install the ISO to a blank disk, follow media-removal instructions and reboot
   into the installed system. Complete normal firstboot with a real test hostname,
   administrator credentials and shop email. Observe the initialization fence
   from outside the appliance before setup and usable application entry afterward.
   For another deployment, exercise its actual initialization trigger separately.
2. Complete the supported hostname and trusted-HTTPS setup. Follow generated
   storefront and administrator links using the configured origin. Check product
   images, CSS and JavaScript, redirects and browser errors. Navigate several
   back-office sections with one session. Reuse a cached browser profile as well
   as checking the relevant fresh navigation. Record functional and visual checks
   separately; inspect customer pages at phone, tablet and desktop widths.
3. In the back office, create a category and product with uploaded image, price,
   stock, shipping and combinations. Open the public friendly category/product
   routes and inspect the actual image response. Select 100 combinations per page,
   change the final row's reference, save the inline list, reload and verify it
   persisted. Also use main product Save and verify its changes after reload.
   This reproduces the reported input boundary; a few variations or API-only
   product creation cannot establish that result.
4. As a customer, choose an in-stock combination, add it to the cart and complete
   an order using a supported offline or sandbox payment method. Verify the order,
   customer, amount and status in the back office and confirm the selected
   combination's stock decrement. Log out and back in and verify retained data.
5. Configure mail through the supported appliance setup and deliver a
   representative message to an actual controlled mailbox. Inspect sender,
   generated links and embedded asset URLs. Complete password recovery through
   the received message; verify the new password works and the old one fails.
   A local receiver or empty Postfix queue alone cannot establish inbox delivery.
6. Install or update a supported free module through the merchant UI. Exercise
   Maintenance: set **Enable store = No**, **Add my IP**, then **Save** before
   opening Update Assistant. Verify its web prerequisites agree with that state.
   End maintenance and verify normal customer access after success or recovery.
7. Back up the seeded files and database. Apply an eligible official update with
   Update Assistant, then repeat merchant navigation, images, last-row combination
   persistence and customer checkout against the preserved data. Restore the
   supported backup and verify pre-backup products, images, orders, credentials
   and stock return. Restart services and reboot; recheck access and stored data.
   If no eligible update exists, record execution as NOT-TESTED with the reason
   and retain the pending upgrade case; discovery alone does not prove an upgrade.

The source sets PHP `max_input_vars` to 2000. The reproduced 100-row inline
request contained 1103 multipart fields; its enclosing product form had 1151
controls. Verify the effective web configuration and actual last-row persistence
in the candidate, including after update. Do not substitute a CLI-only setting
check for the browser case.

## Supporting checks and shared inheritance

`tests/v19.sh` provides runtime smoke checks, including generated image requests,
login, product API operations and updater discovery. The URL refresh regression
runs against the installed shop as the web user:

```sh
runuser -u www-data -- php tests/url-refresh.php
```

Use a disposable shop. It changes domain and icon fixtures, checks generated
routes, preservation of custom icons and `.htaccess` rules, repeat execution
and an unwritable `.htaccess`, then restores fixture data. These checks support
the browser journey; they do not replace installer, merchant, checkout, mail or
maintenance acceptance.

Inherit only a named executed shared case whose artifact/package versions,
configuration and deployment match the candidate. Applicable cases include
static-network DNS persistence, certificate issuance/renewal and recovery, and
platform-specific initialization. Record the exact case and matching inputs
beside the result. Each app still needs its own hostname, HTTPS, permissions and
session interactions. A Core Docker PASS that excludes the installer supplies
no installer coverage.
